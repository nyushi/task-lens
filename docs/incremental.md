# 増分変換と予算

外部`command`変換器は担当（observation.id）ごとに処理します。全担当をまとめて送る旧経路は無効です。
入力・Task・Webの形式は共通ですが、外部CLIのstdin契約はversion 2へ変更しました。
モデルを使わない`observations`、`fixture`は従来どおりです。

## 取得と更新

TUI入力はポーリングです。各回にpane.listを1回、指定paneの現在画面を各1回読みます。
読み取りはローカルで、モデル送信とは別です。現在画面の末尾12,000文字まで保持します。
変更検出は担当別です。取得時刻とrevisionだけの変化は送信理由にせず、本文・状態・連続性等を比較します。
静止待ちで更新をまとめ、最大待機時間を超えると予算内で1回試みます。判定は取得周期ごとなので、実際の待機時間には次の周期までの時間と処理時間が加わります。古い待機から処理し、1回の周期の呼出数も制限します。

初回は現在画面を送ります。ただし文字数上限を超える場合、既定では送信せず保留します。
利用者が`bootstrap_tail_chars`を指定した場合だけ、指定文字数の末尾を部分入力として送ります。
前半は要約済みではありません。部分入力であることと履歴不完全を変換器へ通知します。
初回を小分けに全量送る自動処理はありません。

2回目以降は、最後に採用した画面との差を共通接頭・接尾部分と置換部分で表現します。
これは画面編集であり、追記ログではありません。上書き・削除・スクロールは履歴の消失やタスク完了を意味しません。
前回Taskは対象担当が所有するものだけを渡します。過去の根拠本文は送らず、ID等の参照情報に縮めます。
プロンプト・変更箇所・前回Taskを含む最終JSON全体にバイト上限を適用します。
前回Task自体が大きすぎる場合も保留し、勝手に要約し直したり別モデルを呼んだりしません。

変換後はローカルで再取得し、対象担当の現在版が変わっていれば結果を破棄します。
別担当の変更だけでは破棄しません。連続出力中は破棄が続く場合がありますが、呼出間隔・総予算を超えません。
失敗・破棄した呼出も予算に計上します。

## TUIプロトコルの制約

確認した[公式pane.read定義](https://github.com/herdrdev/herdr/blob/ee5bfb5041bb3e4a49d591c72308aae3c81ecdde/src/api/schema/panes.rs)には
`since_revision`やbyte offsetから差分を再取得する引数がありません。revisionは本文の再取得カーソルではありません。
[イベント仕様](https://github.com/herdrdev/herdr/blob/ee5bfb5041bb3e4a49d591c72308aae3c81ecdde/docs/preview/website/src/content/docs/socket-api.mdx)も
履歴の永続性やsnapshotとの共通シーケンス境界を保証せず、events_lostからの復旧は現在状態の復元です。
イベント購読だけを追加しても欠落した会話本文を復元できません。本実装はまだ購読しません。

TUI入力ではI/O失敗、terminal ID変更、read revisionの巻き戻り、スクロール位置・画面行数変更を検知すると連続性を更新します。
その場合は通常の画面差分を使わず、現在画面全体の再同期を予算内で試みます。上限超過なら保留します。
ポーリング間に表示され消えた文字、同一ID・revisionを保つ検知不能なサーバー再起動は検知・復元できません。
全入力に`historyComplete:false`を付け、履歴の完全性を主張しません。

## 設定

`transform.options`にcommand/argv/prompt_fileと併記します。

| 設定 | 既定値 | 単位・意味 |
|---|---:|---|
| max_input_bytes | 16000 | 呼出ごとのstdin全体のUTF-8 bytes |
| max_output_bytes | 8000 | 呼出ごとのstdout上限 |
| max_total_input_bytes | 128000 | プロセス起動後の累計送信上限 |
| max_total_output_bytes | 64000 | 出力予約量の累計上限 |
| max_calls | 32 | 起動後の呼出数上限 |
| max_calls_per_tick | 2 | 1周期の呼出数上限 |
| max_initial_chars | 2000 | 初回画面の文字数上限 |
| bootstrap_tail_chars | 0 | 0は大量初回を保留。明示指定時のみ末尾を送る |
| quiet_seconds | 30 | 最終変化から静止を待つ秒数 |
| max_wait_seconds | 300 | 連続変化時の待機上限 |
| min_call_seconds | 60 | 同一担当の試行間隔下限 |
| input_price_per_million | 0 | 任意。100万入力tokenの単価 |
| output_price_per_million | 0 | 任意。100万出力tokenの単価 |

バイト予算はtoken数ではありません。毎回max_output_bytes分を予約し、短い応答や失敗でも返却しません。
既定の出力予約総量では最大8呼出で止まります。他の上限が先に効くこともあります。
予算は自動補充しません。メモリ上なので再起動でリセットされます。永続的な課金上限ではありません。
利用者は実行回数・プロンプト・CLI側のmax output tokensも別途管理してください。

## 計測

Webの`/state` JSONに`usage`を追加しています。画面上にも保留数・呼出数を表示し、理由は状態JSONに担当別で出します。
`input_bytes`は実際にCLIへ渡したJSON長、`output_bytes`は取得できたstdout長です。
プロセス異常終了時の失われた出力は計測できません。`reserved_output_bytes`が安全側の予約量です。
`estimated_cost`は入力bytesと出力予約bytesをtoken数の代用値として設定単価で計算します。
これは粗い予算参考値で、実token数・実請求額・厳密な費用上限ではありません。単価未設定の0は無料という意味ではありません。
CLI独自の追加プロンプト・推論token・ツール・再試行・外部アクセスはこの計測に入りません。
ラッパーが別データを取得しないことと、プロバイダー側の使用量・制限を別途確認してください。

## 所有と依存関係

出力IDは入力namespaceで始めます。担当内の複数Taskと再帰ツリーは使用できます。
別担当のTaskを上書き・参照する出力は拒否します。担当間の依存は未解決事項としてtextで残します。
依存先の変更を受けた自動再要約や全担当統合は未実装です。勝手に他担当の全状態を追加送信しません。
消えた担当・更新待ちのTaskはstaleになり、前回の有効な結果を保持します。
